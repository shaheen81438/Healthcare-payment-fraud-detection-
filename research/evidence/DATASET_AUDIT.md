# Dataset audit

This audit describes the local files available at generation time. Detailed schema, dtypes, missing counts and unique counts are in `TABLES/DATASET_COLUMN_QUALITY.csv`; file sizes, dimensions and row duplicate counts are in `DATASET_SUMMARY.csv`. Reports intentionally exclude record values and identifiers.

## Preprocessing, labels, and provenance

The generator configuration uses seed 42, a 24-month start at 2024-01, 2,000 configured providers, 40,000 configured beneficiaries, and configurable injected patterns and raw-data defects. `configs/features.yaml` specifies a temporal split: burn-in through 2024-03, training through 2025-03, validation through 2025-06, then test. The documented pipeline fits preprocessing and peer statistics on training data; validation is used for calibration/selection. Leakage tests and generator/label assumptions are documented in `docs/labeling.md` and `configs/`.

The committed demo claim artifact has fewer rows than the generator configuration suggests; it is a sample/scored subset and should not be described as the full synthetic population. The committed evaluation scores/labels form a complete matched evaluation set. The exact original training hardware, runtime, and installed package set used to create those frozen scores are not present in artifact metadata.

CMS is a real external calibration context, not a source of claim labels. The project does not contain official LEIE rows. CMS CERT measures improper payments, which are broader than fraud; it is not used as evaluation ground truth here ([CMS CERT](https://www.cms.gov/data-research/monitoring-programs/improper-payment-measurement-programs/comprehensive-error-rate-testing-cert), [CERT background](https://www.cms.gov/data-research/monitoring-programs/improper-payment-measurement-programs/comprehensive-error-rate-testing-cert/background)).
